## Соответствие требованиям

| Требование | Реализация и доказательство |
| --- | --- |
| Модульные тесты | `tests/unit/`: доменные сущности, value objects, сервисы, обработчики команд и запросов, инфраструктурные адаптеры и HTTP-обработчики. |
| Интеграционные тесты | `tests/integration/conftest.py` создаёт временные PostgreSQL 16 и Redis 7, применяет миграции Alembic и проверяет отсутствие расхождений схемы с моделями. HTTP-тесты вызывают собранное приложение с настоящими зависимостями. |
| Сценарии переходов состояний из лабораторной № 1 | `tests/integration/http/v1/routes/test_learning.py::test_learning_lifecycle_and_history`: создание конфигурации, колоды и карточки → очередь → оценки → LEARNING → REVIEW → RELEARNING → REVIEW → сброс → новый объект прогресса. Создание NEW и матрица четырёх состояний и четырёх оценок дополнительно проверены в `tests/unit/domain/card_progress/services/test_card_progress_service.py`. |
| Arrange–Act–Assert и понятные названия | Например, `tests/unit/application/commands/card_progress/test_review_card.py::test_reviews_existing_progress`: подготовка сущностей и моков → вызов обработчика → проверка результата, записи истории и commit. HTTP-сценарии содержат последовательные действия и проверки каждого этапа. |
| Параметризованные тесты | Матрица состояний и оценок, пустые шаги переучивания, корректные и некорректные значения в `tests/unit/domain/`. |
| Негативные тесты и границы | Пустые, слишком короткие и длинные имена/пароли, доменные исключения, отсутствующие сущности, повторный email, 401/403 при отказе в доступе, 422 на неверный вопрос и оценку. |
| Независимость | Юнит-фикстуры создают новые моки для каждого теста; HTTP-клиент создаётся на тест, данные пользователей имеют случайные идентификаторы. Интеграционная БД общая для сессии, тесты создают собственные данные. Полный набор проверен в обычном и обратном порядке, результаты совпали. Это проверка двух порядков, а не доказательство для всех возможных перестановок. |
| Моки в модульных тестах | `tests/unit/application/conftest.py`: `Mock`, `AsyncMock`, `create_autospec` для gateway, сервисов и транзакций. |
| Заглушки исходящих HTTP-запросов | В текущей версии нет исходящих HTTP-интеграций с внешними сервисами. PostgreSQL и Redis используют собственные протоколы и проверяются настоящими контейнерами. `ASGITransport` вызывает тестируемое приложение и не является заглушкой внешнего сервиса. Пункт неприменим к текущей реализации; если преподаватель требует демонстрацию заглушек безусловно, этот пункт остаётся незакрытым. |
| Покрытие не ниже 70% | `pytest-cov`, измерение строк и ветвей, обязательный `fail_under = 70` в `pyproject.toml`. Обычный запуск pytest и существующий шаг CI используют этот порог. |
| Исключения из покрытия | Измеряется только `src/trafficmaster`; исключены `setup/config/*` и `infrastructure/persistence/migrations/*`. Отдельного сгенерированного кода приложения не обнаружено. |

## Воспроизведение

Нужны зависимости группы dev и доступный Docker daemon. При уже установленном окружении:

```bash
.venv/bin/pytest tests/ -q --cov-report=term-missing --cov-report=html --cov-report=xml
```

Результаты покрытия сохраняются в `htmlcov/index.html` и `coverage.xml`. При результате ниже 70% команда завершается с ошибкой. Для локального запуска отдельных модулей используйте `--no-cov`: порог установлен для полного набора приложения.

Для повторения проверки обратного порядка можно создать временный pytest-плагин:

```bash
cat > /tmp/trafficmaster_lab2_reverse.py <<'PY'
def pytest_collection_modifyitems(items):
    items.reverse()
PY
PYTHONPATH=/tmp .venv/bin/pytest tests/ -p trafficmaster_lab2_reverse -q --no-cov
```
