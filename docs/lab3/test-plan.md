# План тестирования TrafficMaster — ЛР3

Версия 1.0, 16.11.2026. Объект: текущее рабочее дерево backend TrafficMaster. Спецификация: [ЛР1](../requirements.md); базовая автоматизация: [ЛР2](../lab2-verification.md). Исполнитель: агент в локальном окружении проекта; пользователь рассматривает итоговые материалы и принимает решение о приёмке. Часовой пояс протокола — Europe/Minsk.

## Цель и риски

Проверить, что пользователь может безопасно войти, подготовить учебный материал, повторять его с корректными переходами CardProgress, видеть собственный прогресс и удалять материалы. Выявить расхождения с FR/NFR, воспроизводимо зарегистрировать их и подготовить доказательства. Основные риски: утечка чужих приватных данных, потеря/смешение прогресса, неверный расчёт очереди и лимитов, несогласованность API и БД. Цель тестирования не равна доказательству эффективности подготовки к экзамену.

### Исключения и основания

| Исключение | Связь с требованиями и обоснование |
| --- | --- |
| Отдельный frontend, визуальная совместимость браузеров, мобильный UI | Не заявлены ни одним FR. Приёмочный интерфейс ЛР1 — API/Swagger. Снимки отчёта подтверждают результаты, но не являются UI-тестами продукта. |
| Загрузка/выдача файлов изображений | FR-12 требует только строку image_path; хранилище файлов не реализовано. |
| Keycloak, исходящие HTTP-сервисы, cache-aside | Не входят в FR; отсутствуют в реализации. HTTP-заглушки для несуществующей интеграции не создаются. Redis проверяется по его протоколу. |
| Официальный экзамен, актуальность ПДД, импорт билетов, образовательная эффективность | Вне границ спецификации ЛР1; ни один FR не обещает этих функций. |
| Нагрузка, длительный soak, конкурирующие транзакции и гонки | Будущий этап. FR-15 проверяет запись прогресса/лога последовательно; NFR-06 не задаёт нагрузку. Без SLA нельзя объявить соответствие скорости. Перед будущим этапом согласовать число пользователей, RPS, p95, допустимый error rate и конфигурацию стенда. |
| Перезапуск хоста, восстановление backup, production-deploy | Явно вне NFR-06. NFR-05 проверяется валидаторами конфигурации, а не развёртыванием production. |
| Полный pentest и административная ролевая матрица | NFR-02/03 проверяются в заявленных обычных пользовательских сценариях; это не аудит всей безопасности. Администрирование вне обязательных UR ЛР1. |
| Физическое отключение контейнеров для fault injection | NFR-04: ошибки/тайм-ауты моделируются в unit-тестах; штатная readiness — на реальных сервисах. Реальное отключение БД/Redis — будущий системный этап, его результат не объявляется полученным. |
| just up и Docker image build | Не являются FR. Сетевой сервер запускается напрямую. Полный рецепт just и сборка образа остаются вне этого прогона; DOC-01/02 имеют соответствующие ограничения повторной проверки. |

## Стратегия и инструменты

| Уровень / вид | Инструменты и данные | Состояние |
| --- | --- | --- |

| Интеграционное | PostgreSQL 16, Redis 7, Testcontainers, Alembic; настоящие persistence-адаптеры | Реализовано; временные контейнеры, миграции на пустой БД. |
| API и системное автоматизированное | Uvicorn отдельным процессом на свободном localhost-порту; HTTPX по TCP; 42 кейса каталога | Выполняется для ЛР3; сохранение запросов/ответов и проверок. |
| Сценарное | Цепочки API, reset и новый объект; два пользователя; копирование | Реализовано. |
| Системное ручное / исследовательское | Swagger UI: ручное повторение шагов опубликованных кейсов; перезапуск и проверка окружения | Шаги подготовлены; отдельный полный ручной прогон всех кейсов не заявляется. |
| UI | Браузерный просмотр реального отчёта и снимки результатов; продуктовый frontend отсутствует | Снимки — доказательства API-прогона, не метрика UI-покрытия. |
| Нагрузочное | Будущие k6/Locust после согласования SLA и стенда | Не выполнялось, результатов нет. |
| Регрессионное, функциональное, негативное, граничное, авторизация | pytest, 20 пар позитив/негатив, два допустимых длинных значения, проверки UTC | Текущий объём. |
| Статическое | Ruff, mypy; инспекция транзакции и трассировки требований; синтаксис и ссылки документации | Дополняет динамические проверки, не заменяет их. |
| Покрытие | pytest-cov, coverage.py, порог 70%; исключены конфигурация и миграции | Полный прогон; метрика кода отделена от покрытия требований. |

Сначала выполняется smoke (миграции, readiness), затем доступ и CRUD, после — обучение и изоляция. Каждый кейс создаёт собственные сущности и HTTP-клиент. БД общая для сессии, тесты не опираются на результаты предыдущих кейсов; имена и email уникальны. Перестановка проверяется отдельно. В случаях TC-025/027 время целевых строк изменяется непосредственно в одноразовой БД, чтобы проверить категории и UTC-границу без ожидания суток. Эти SQL-действия отражены в трассе и не выдаются за пользовательские HTTP-операции. Они затрагивают только карточки соответствующего кейса.

## Окружение, данные и артефакты

Python >=3.12 и зависимости из uv.lock, Docker daemon, свободный localhost-порт; точные версии фактического прогона находятся в [протоколе](execution.md). Используются синтетические аккаунты, пароль LearningSecure123, случайные email/UUID. Производственные данные не используются. Пароли и cookie не записываются в HTTP-трассы. Набор M и шаги описаны в [каталоге кейсов](test-cases.md), исполняемая реализация — `tests/integration/lab3/test_acceptance.py`.

Артефакты: [чек-лист](checklist.md), [каталог](test-cases.md), [протокол и метрики](execution.md), JSON-трассы и скриншоты в evidence/, HTML-отчёт, реестр ISSUES.md. Состояния кейсов: Not run, Passed, Failed, Blocked; xfail в pytest для известного дефекта соответствует **Failed** в приёмочном протоколе.

## Критерии, выраженные через метрики

| Критерий | Условие |
| --- | --- |
| Начало | 20/20 FR имеют приоритет; 20/20 покрыты кейсами; у каждого FR ≥1 позитивного и ≥1 негативного кейса; ≥25 кейсов содержат все обязательные поля; 100% smoke-проверок (миграции и readiness) успешны; блокирующих дефектов стенда =0. |
| Приостановка | ≥1 блокирующий дефект стенда (невозможны миграция, запуск или readiness); либо число Blocked >10% запланированных кейсов; либо ≥1 инцидент утечки реальных данных. Одиночный продуктовый Failed регистрируется, остальные независимые кейсы продолжаются. |
| Возобновление | Блокирующих дефектов стенда =0; smoke повторно пройден на 100%; все ранее Blocked кейсы имеют восстановленные предусловия (100%); после остановки нет нерасследованных инцидентов. |
| Завершение тестирования | Выполнено 100% каталога; Blocked=0, Not run=0; 100% Failed имеют зарегистрированный дефект; 100% кейсов имеют фактический результат, трассу и скриншот; метрики рассчитаны; все вновь обнаруженные дефекты классифицированы. Завершение прогона допускает отрицательное решение о приёмке. |
| Приёмка продукта | Высокоприоритетные кейсы Passed=100%; общий pass rate ≥95%; покрытие всех FR кейсами=100%; открытых S1/S2=0; каждый принимаемый FR прошёл все связанные кейсы; покрытие кода ≥70%. Открытые S3/S4 требуют явного решения владельца о переносе; автоматического согласия нет. |

Для текущего плана все 20 FR обязательны; High задаёт критический пользовательский поток, Medium — изменение/статистику. Выявленный дефект FR-01 не скрывается общим высоким pass rate. Приёмку и завершение тестирования оценивают отдельно.

## Метрики и формулы

Обозначения: N — все запланированные кейсы; P — Passed; F — Failed; B — Blocked; U — Not run; E=P+F — реально выполненные; R — все FR в объёме; Rc — FR, связанные хотя бы с одним оформленным кейсом; Rp — FR, у которых все связанные кейсы Passed; Ds — зарегистрированные дефекты важности s; Vs — из них исправленные и подтверждённые повторной проверкой. Не считать xfail успешным и не включать Blocked в E. Проверка не является Failed, если не удалось выполнить её предусловия.

- **Процент выполнения кейсов:** E/N × 100%.
- **Процент успешного прохождения:** P/E × 100%.
- **Покрытие требований кейсами:** Rc/R × 100%.
- **Процент требований с успешной проверкой:** Rp/R × 100% (дополнительная метрика).
- **Процент устранения дефектов по важности:** Vs/Ds × 100%, отдельно S1, S2, S3, S4. В числитель не попадают «исправлен, не перепроверен» и принятые к переносу дефекты.
- **Успешность High-кейсов:** P_high/(P_high+F_high) × 100%.

При нулевом знаменателе результат N/A, не 100%. Покрытие FR не означает их успешность; покрытие строк не заменяет покрытие требований. Реестр дефектов имеет фиксированный состав, указанный в протоколе, чтобы исторические исправления не меняли знаменатель скрытно.

Методичка и её раздел 6.2 не предоставлены. Использованы явно заданные стандартные отношения счётчиков; дословное соответствие обозначениям и принятому в пособии знаменателю для успешности не подтверждается. Приведены исходные числа, позволяющие пересчитать показатели по пособию.

## Дефекты и порядок повторной проверки

S1 Blocker — основной поток/стенд недоступен; S2 Critical — утрата данных, нарушение изоляции либо основной функции без приемлемого обхода; S3 Major — ограниченный набор данных/функция не работает, обход есть; S4 Minor — косметика/неточность документации. Срочность отдельна: P1 — ближайшее исправление до релиза, P2 — плановое, P3 — низкая. Приоритет FR/кейса High/Medium не равен severity дефекта.

Каждый дефект включает ID, требование, краткое и подробное описание, ожидание/факт, исходные данные и шаги, воспроизводимость, S/P, симптом, обход и статус повторной проверки. После исправления APP-01/02 нужны миграции и повтор TC-041/042 без xfail, проверка обычной регистрации и полный регрессионный прогон. Не объявлять эти дефекты исправленными на основании существования теста.
