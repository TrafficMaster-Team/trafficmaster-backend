Проверка: 16.11.2026. Спецификация: [requirements.md](docs/requirements.md); методы и результаты: [verification.md](docs/verification.md). Открытые дефекты остаются видимыми, исправленные сохранены как история верификации.

## APP-01 — Регистрация отклоняет корректный email длиннее 50 символов

- **Статус: открыт. Приоритет: средний. Требование: FR-01, UR-01.**
- Предусловие: новая БД с миграциями, гость без cookie.
- Шаги: `POST /v1/auth/signup` с `email=valid-address-longer-than-fifty-characters-123@example.com`, `name=Valid-Name`, `password=LearningSecure123`.
- Ожидается: 201 с ID, поскольку корректный адрес проходит HTTP EmailStr и укладывается в предел 254.
- Фактически: 401 `Authentication failed`; в БД email задан как VARCHAR(50), ошибка длины скрыта как ошибка аутентификации.
- Причина: `infrastructure/persistence/models/users.py` и схема миграций не согласованы с допустимой длиной HTTP email.
- Проверка: `test_registration_accepts_valid_long_identity[email]` — strict xfail. `--runxfail` воспроизводит обычное падение.
- Рекомендация: согласовать ограничение длины в HTTP/domain/БД и добавить миграцию; отдельно уточнить обработку ошибки сохранения. Не исправлено в рамках подготовки материалов лабораторной.


- **Важность / срочность (ЛР3): S3 Major / P2.** Ограниченный набор допустимых входных данных блокирует регистрацию; обычная регистрация работает.
- **Воспроизводимость:** 1/1 в актуальном прогоне TC-041; также воспроизведён ранее strict xfail. Гость, чистые cookie, уникальный email в новой временной БД.
- **Симптом:** HTTP 401 вместо 201 при регистрации допустимого длинного email; это ошибка согласования данных и ошибочная классификация сбоя сохранения.
- **Обход:** использовать принадлежащий пользователю корректный email длиной ≤50; если такого адреса нет, обхода для исходного адреса нет.
- **ЛР3:** TC-041, результат Failed; требование [FR-01](docs/requirements.md), трасса `docs/lab3/evidence/TC-041.json`. Статус Open; повторная проверка исправления не выполнялась, исправления нет.

## APP-02 — Принимаемое API имя длиной 21…30 не помещается в БД

- **Статус: открыт. Приоритет: средний. Требование: FR-01, UR-01.**
- Предусловие: гость и уникальный короткий email.
- Шаги: signup с именем `ValidUsernameLongerThan20` (24 символа), корректными email и паролем.
- Ожидается: 201 — длина находится в диапазоне 5…30 HTTP-схемы, символы допустимы.
- Фактически: 401 `Authentication failed`; `users.name` имеет VARCHAR(20). Domain допускает до 255, что также требует согласования с публичным контрактом.
- Проверка: `test_registration_accepts_valid_long_identity[username]` — strict xfail.
- Рекомендация: выбрать единое ограничение, изменить модель/миграцию и согласовать схемы. Не исправлено в рамках подготовки материалов лабораторной.


- **Важность / срочность (ЛР3): S3 Major / P2.** Отказ регистрации для части допустимых имён, обход — короткое имя.
- **Воспроизводимость:** 1/1 в актуальном прогоне TC-042; ранее strict xfail. Создать новый уникальный email, очистить cookie, отправить POST /v1/auth/signup с name=ValidUsernameLongerThan20 и password=LearningSecure123.
- **Симптом:** HTTP 401 вместо 201 для имени длиной 24, проходящего контракт API; несогласованность валидации и схемы БД.
- **Обход:** допустимое имя длиной 5…20.
- **ЛР3:** TC-042, результат Failed; [FR-01](docs/requirements.md), трасса `docs/lab3/evidence/TC-042.json`. Статус Open; исправления и повторной проверки после него нет.

## APP-03 — Непустая очередь не сериализовала варианты ответов

- **Статус: исправлен и проверен. Приоритет: высокий. Требования: UR-05, FR-11, FR-13.**
- Воспроизведение до исправления: создать карточку с answerOptions, получить `/v1/review/queue?deck_id=...`.
- Ожидалось: 200 и карточка с вариантами ответа.
- Фактически: ValidationError вложенного `AnswerOptionResponseSchema` при передаче `AnswerOptionView`; ошибка сервера вместо ответа очереди.
- Исправление: включён `from_attributes=True` у схемы ответа варианта.
- Повторная проверка: I-LIFE, I-LIMIT и I-SHARE проходят на реальном PostgreSQL; создание, чтение и выдача очереди возвращают корректные варианты.


- **Важность / срочность (ЛР3): S2 Critical / P1.** Основная выдача учебной очереди не работала для карточек с вариантами.
- **Подробные шаги:** зарегистрировать пользователя и войти; создать конфигурацию и свою колоду; POST /v1/card/ с question, answerOptions=[{text: Stop, isCorrect: true, rationale: Red prohibits movement}], hint; GET /v1/review/queue?deck_id=<ID колоды>.
- **Воспроизводимость:** исторический дефект воспроизводился до изменения response-схемы; численный счётчик прежних попыток не сохранён. На текущей версии 0/1 по TC-025, а также 0/1 по TC-027/028; регрессия не воспроизведена.
- **Симптом:** серверная ошибка сериализации ответа очереди.
- **Обход:** полноценного пользовательского обхода для очереди не было; прямое чтение карточки не заменяет планировщик обучения.
- **Повторная проверка:** TC-025/027/028, статус Verified fixed. Требования [FR-11/13](docs/requirements.md). Исторический сбой не выдаётся за наблюдённый на текущем коммите.

## APP-04 — Копирование колоды нарушало порядок вставки зависимостей

- **Статус: исправлен и проверен. Приоритет: высокий. Требования: BR-03, UR-04, FR-10.**
- Воспроизведение до исправления: второй пользователь копирует публичную колоду с карточкой через `POST /v1/deck/{id}/copy`.
- Ожидалось: 201 и независимая приватная копия.
- Фактически: нарушение FK `cards.deck_id → decks.id`, копия не сохранялась.
- Причина: ORM mappings без relationships не обеспечивали требуемый порядок зависимых вставок при едином commit.
- Исправление: flush новой конфигурации, затем flush колоды, затем карточки и общий commit. Промежуточные flush не фиксируют транзакцию.
- Повторная проверка: I-SHARE — проверены владелец, приватность, новые ID и карточка в копии.


- **Важность / срочность (ЛР3): S2 Critical / P1.** Основной сценарий повторного использования колоды не завершался.
- **Подробные шаги:** A регистрируется и создаёт конфигурацию, публичную колоду и карточку; очистить cookie; зарегистрировать/авторизовать B; POST /v1/deck/<ID колоды A>/copy.
- **Воспроизводимость:** исторически воспроизводился до добавления промежуточных flush; число старых попыток не сохранено. На текущей версии 0/1 по TC-019.
- **Симптом:** ошибка FK на cards.deck_id и отсутствие сохранённой копии.
- **Обход:** вручную создать свою конфигурацию/колоду и переписать карточки; автоматическое копирование обходом не восстанавливается.
- **Повторная проверка:** TC-019, статус Verified fixed; [FR-10](docs/requirements.md). Историческое воспроизведение и текущая регрессия разделены.

## DOC-01 — Keycloak занимал порт API

- **Статус: исправлен по конфигурации. Приоритет: высокий.**
- До исправления Compose публиковал Keycloak на 8080, который назначен API в `.env.dist` и README.
- Исправление: сервис Keycloak и его переменные удалены, поскольку приложение использует собственную аутентификацию.
- Проверка: `docker compose --env-file .env.dist -f docker-compose-local.yaml config --services` содержит только postgres и redis. Реальный сервер на отдельном свободном порту проверен I-RUN. Полный локальный запуск через just не выполнялся.


- **Важность / срочность (ЛР3): S2 Critical / P1.** Конфликт порта мешал запуску по инструкции.
- **Связь:** окружение исполнения [NFR-06](docs/requirements.md); отдельного FR на just/Compose нет, дефект инструкции.
- **Шаги на прежней версии:** поднять прежний Compose с Keycloak на 8080; запустить API с UVICORN_PORT=8080.
- **Ожидаемый результат:** оба требуемых сервиса запускаются без конфликтов. **Фактический до исправления:** порт занят Keycloak, сервер API не может его использовать.
- **Воспроизводимость:** по старой конфигурации воспроизводимо при занятом 8080; счётчик запусков не сохранён. В текущей конфигурации конфликт удалён; полный прежний сценарий не повторён.
- **Симптом:** отказ привязки API к порту. **Обход до исправления:** другой свободный порт API и согласование URL.
- **Статус для метрик ЛР3:** Resolved, awaiting full retest; не включён в числитель подтверждённо устранённых дефектов. Проверка конфигурации не равна полному запуску инструкции.

## DOC-02 — README не указывал just и корректную работу с окружением

- **Статус: исправлен в инструкции; проверка just не выполнена. Приоритет: средний.**
- До исправления just отсутствовал в prerequisites, рецепт uvicorn рассчитывал на глобальный PATH; команда миграций не загружала `.env`.
- Исправление: just указан в README, рецепт использует `.venv/bin/uvicorn`, миграции — `uv run --env-file .env`; добавлены прямые команды без just. Для API на хосте REDIS_HOST изменён на localhost.
- Проверка: инспекция README/Justfile и конфигурации; исполняемые файлы доступны в `.venv`. В окружении проверки just не установлен, поэтому выполнение самого рецепта остаётся непроверенным.


- **Важность / срочность (ЛР3): S3 Major / P2.** Инструкция зависела от неописанных инструментов и окружения.
- **Связь:** воспроизводимость окружения [NFR-06](docs/requirements.md); отдельный FR на just не заявлен.
- **Шаги на прежней версии:** выполнить README на машине без just и глобального uvicorn; при миграции не экспортировать .env вручную.
- **Ожидаемый результат:** предпосылки перечислены, приведённые команды находят исполняемые файлы и настройки. **Фактический до исправления:** отсутствующий just/uvicorn либо настройки БД не загружены.
- **Воспроизводимость:** зависит от чистоты окружения; старый численный счётчик отсутствует. В текущем окружении just не установлен, полный повтор рецепта не выполнен.
- **Симптом:** ошибка команды/конфигурации запуска. **Обход:** прямые команды через .venv и явная загрузка окружения, приведённые в обновлённой инструкции.
- **Статус для метрик ЛР3:** Resolved, awaiting full retest; в числитель Verified fixed не включён.

## DOC-03 — Схема данных ошибочно изображала физическую связь прогресса и истории

- **Статус: исправлен и проверен инспекцией. Приоритет: низкий.**
- До исправления схема изображала `CardProgress → ReviewLog` как прямую связь БД.
- Исправление: показаны FK `User → ReviewLog` и `Card → ReviewLog`; связь с прогрессом объяснена как логическая по user_id/card_id.
- Проверка: сопоставление с ORM-моделями review_logs/card_progress; I-LIFE дополнительно подтверждает сохранение истории при сбросе прогресса.


- **Важность / срочность (ЛР3): S4 Minor / P3.** Неточность схемы документации, исполнение не нарушалось.
- **Связь:** описание хранения [FR-17/19, NFR-06](docs/requirements.md).
- **Шаги:** открыть старую схему данных; сравнить связь CardProgress→ReviewLog с FK в models/review_logs.py; сбросить прогресс и прочитать логи.
- **Ожидаемый результат:** схема отражает реальные FK User/Card→ReviewLog и сохранение истории после reset. **Фактический до исправления:** показана несуществующая физическая связь от CardProgress.
- **Воспроизводимость:** 1/1 при инспекции исторической схемы; число runtime-попыток неприменимо.
- **Симптом:** неверная архитектурная информация. **Обход:** сверяться с ORM и миграциями.
- **Повторная проверка:** исправленная схема сверена с ORM ранее; TC-037 подтверждает сохранение истории после reset. Статус Verified fixed, историческая инспекция учтена отдельно от API-прогона.

## DOC-04 — Документация описывала отсутствующий Redis cache-aside

- **Статус: исправлен и проверен инспекцией. Приоритет: средний.**
- До исправления overview, configuration, development и index обещали decorators, fallback и invalidation.

- Проверка: поиск обращений к CacheStore и просмотр регистрации gateway в `setup/ioc.py`; бизнес-обработчики работают с SQLAlchemy gateway напрямую.


- **Важность / срочность (ЛР3): S3 Major / P2.** Документация обещала отсутствующее поведение интеграции.
- **Связь:** диагностика [NFR-04](docs/requirements.md); предметное кэширование не является FR и исключено границами ЛР1.
- **Шаги:** открыть прежние overview/configuration/development/index; найти обещания cache-aside; найти обращения бизнес-gateway к CacheStore и регистрацию адаптеров в setup/ioc.py.
- **Ожидаемый результат:** документация описывает фактически используемые адаптеры и границы версии. **Фактический до исправления:** заявлены decorators/fallback/invalidation, которых нет в предметном пути запросов.

- **Повторная проверка:** исправленные тексты сверены с gateway и IoC ранее; статус Verified fixed по инспекции. Этот дефект не объявляется закрытым HTTP-кейсом.

Отсутствие загрузки изображений — согласованная граница версии, не дефект текущей спецификации. Наличие двух открытых дефектов означает, что FR-01 пока не принят полностью; остальные проверенные результаты перечислены отдельно в матрице.
