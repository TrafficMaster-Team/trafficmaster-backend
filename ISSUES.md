## APP-01 — Регистрация отклоняет корректный email длиннее 50 символов

- **Статус: открыт. Приоритет: средний. Требование: FR-01, UR-01.**
- Предусловие: новая БД с миграциями, гость без cookie.
- Шаги: `POST /v1/auth/signup` с `email=valid-address-longer-than-fifty-characters-123@example.com`, `name=Valid-Name`, `password=LearningSecure123`.
- Ожидается: 201 с ID, поскольку корректный адрес проходит HTTP EmailStr и укладывается в предел 254.
- Фактически: 401 `Authentication failed`; в БД email задан как VARCHAR(50), ошибка длины скрыта как ошибка аутентификации.
- Причина: `infrastructure/persistence/models/users.py` и схема миграций не согласованы с допустимой длиной HTTP email.
- Проверка: `test_registration_accepts_valid_long_identity[email]` — strict xfail. `--runxfail` воспроизводит обычное падение.
- Рекомендация: согласовать ограничение длины в HTTP/domain/БД и добавить миграцию; отдельно уточнить обработку ошибки сохранения. Не исправлено в рамках подготовки материалов лабораторной.


- **Важность / срочность (ЛР3): S3 Major / P2.** Ограниченный набор допустимых входных данных блокирует регистрацию; обычная регистрация работает.
- **Воспроизводимость:** 1/1 в актуальном прогоне TC-041; также воспроизведён ранее strict xfail. Гость, чистые cookie, уникальный email в новой временной БД.
- **Симптом:** HTTP 401 вместо 201 при регистрации допустимого длинного email; это ошибка согласования данных и ошибочная классификация сбоя сохранения.
- **Обход:** использовать принадлежащий пользователю корректный email длиной ≤50; если такого адреса нет, обхода для исходного адреса нет.
- **ЛР3:** TC-041, результат Failed; требование [FR-01](docs/requirements.md), трасса `docs/lab3/evidence/TC-041.json`. Статус Open; повторная проверка исправления не выполнялась, исправления нет.

## APP-03 — Непустая очередь не сериализовала варианты ответов

- **Статус: исправлен и проверен. Приоритет: высокий. Требования: UR-05, FR-11, FR-13.**
- Воспроизведение до исправления: создать карточку с answerOptions, получить `/v1/review/queue?deck_id=...`.
- Ожидалось: 200 и карточка с вариантами ответа.
- Фактически: ValidationError вложенного `AnswerOptionResponseSchema` при передаче `AnswerOptionView`; ошибка сервера вместо ответа очереди.
- Исправление: включён `from_attributes=True` у схемы ответа варианта.
- Повторная проверка: I-LIFE, I-LIMIT и I-SHARE проходят на реальном PostgreSQL; создание, чтение и выдача очереди возвращают корректные варианты.


- **Важность / срочность (ЛР3): S2 Critical / P1.** Основная выдача учебной очереди не работала для карточек с вариантами.
- **Подробные шаги:** зарегистрировать пользователя и войти; создать конфигурацию и свою колоду; POST /v1/card/ с question, answerOptions=[{text: Stop, isCorrect: true, rationale: Red prohibits movement}], hint; GET /v1/review/queue?deck_id=<ID колоды>.
- **Воспроизводимость:** исторический дефект воспроизводился до изменения response-схемы; численный счётчик прежних попыток не сохранён. На текущей версии 0/1 по TC-025, а также 0/1 по TC-027/028; регрессия не воспроизведена.
- **Симптом:** серверная ошибка сериализации ответа очереди.
- **Обход:** полноценного пользовательского обхода для очереди не было; прямое чтение карточки не заменяет планировщик обучения.
- **Повторная проверка:** TC-025/027/028, статус Verified fixed. Требования [FR-11/13](docs/requirements.md). Исторический сбой не выдаётся за наблюдённый на текущем коммите.

## APP-04 — Копирование колоды нарушало порядок вставки зависимостей

- **Статус: исправлен и проверен. Приоритет: высокий. Требования: BR-03, UR-04, FR-10.**
- Воспроизведение до исправления: второй пользователь копирует публичную колоду с карточкой через `POST /v1/deck/{id}/copy`.
- Ожидалось: 201 и независимая приватная копия.
- Фактически: нарушение FK `cards.deck_id → decks.id`, копия не сохранялась.
- Причина: ORM mappings без relationships не обеспечивали требуемый порядок зависимых вставок при едином commit.
- Исправление: flush новой конфигурации, затем flush колоды, затем карточки и общий commit. Промежуточные flush не фиксируют транзакцию.
- Повторная проверка: I-SHARE — проверены владелец, приватность, новые ID и карточка в копии.


- **Важность / срочность (ЛР3): S2 Critical / P1.** Основной сценарий повторного использования колоды не завершался.
- **Подробные шаги:** A регистрируется и создаёт конфигурацию, публичную колоду и карточку; очистить cookie; зарегистрировать/авторизовать B; POST /v1/deck/<ID колоды A>/copy.
- **Воспроизводимость:** исторически воспроизводился до добавления промежуточных flush; число старых попыток не сохранено. На текущей версии 0/1 по TC-019.
- **Симптом:** ошибка FK на cards.deck_id и отсутствие сохранённой копии.
- **Обход:** вручную создать свою конфигурацию/колоду и переписать карточки; автоматическое копирование обходом не восстанавливается.
- **Повторная проверка:** TC-019, статус Verified fixed; [FR-10](docs/requirements.md). Историческое воспроизведение и текущая регрессия разделены.

## APP-05 — Обычный пользователь может назначить себе роль администратора

- **Статус:** Open. **Важность:** S2 Critical. **Срочность:** P1, исправить до публикации API.
- **Требование:** базовая безопасность ЛР4, пункт 3; [NFR-02 и модель актёров ЛР1](docs/requirements.md). Обычный пользователь не должен сам получать административные полномочия.
- **Краткое описание:** PATCH собственного идентификатора в административной ручке повышает роль без административного разрешения.
- **Подробное описание / ожидаемый результат:** авторизованный USER вызывает `PATCH /v1/user/{свой UUID}/admin`; ожидается 403, роль остаётся `user`.
- **Фактический результат:** 204; последующий `/v1/auth/me` возвращает `role=admin`. Это фактическое изменение роли, а не только неверный код ответа.
- **Исходные данные:** свежий пользователь B с обычной ролью USER; cookie из собственного login; знание чужих идентификаторов не требуется.
- **Шаги:** зарегистрировать B; войти; получить свой ID через me; вызвать PATCH собственного `/admin`; снова вызвать me.
- **Воспроизводимость:** 1/1 в итоговом прогоне ЛР4, запросы R127/R128. Данные и последующие полномочия проверялись только в одноразовом стенде. После воспроизведения роль B возвращена в USER отдельным привилегированным тестовым аккаунтом (R129).
- **Симптом:** вертикальное повышение привилегий через прямой вызов API.
- **Причина по инспекции:** `GrantAdminByIdCommandHandler` использует общий `can_manage_user`, который разрешает управление собой; отдельной проверки права назначения роли нет.
- **Обход:** надёжного пользовательского обхода нет; до исправления ограничить доступ к административным операциям на доверенной границе и не предоставлять API недоверенным клиентам. Скрытие кнопки в UI не является защитой.
- **Доказательства:** [Postman HTML-отчёт](docs/lab4/evidence/newman.html), запросы R127/R128; [JSON](docs/lab4/evidence/newman.json). Исправление не выполнялось в рамках задания по тестированию.

## APP-06 — OpenAPI описывает неверную структуру ответов 401 и 422

- **Статус:** Open. **Важность:** S3 Major. **Срочность:** P2.
- **Требование:** ЛР4, пункт 2 — проверка структуры ответа по контракту; FR-01/07/11/15 и NFR-02 для соответствующих операций. Коды отказа сами по себе корректны, проблема в документированном формате.
- **Краткое описание:** заявлены `ExceptionSchema` / `ExceptionSchemaRich` с обязательным `description`, фактические штатные ошибки FastAPI возвращаются с `detail`.
- **Ожидаемый результат:** HTTP-ответ соответствует опубликованной JSON Schema либо контракт явно описывает обе допустимые формы.
- **Фактический результат:** например, `GET /v1/auth/me` без cookie → 401 `{"detail":"Not authenticated"}`; `POST /v1/auth/signup` с некорректным email → 422 `{"detail":[...]}`. OpenAPI требует `description`, поэтому schema-assertions не проходят.
- **Исходные данные:** гость без cookie; для 422 — email=invalid, name=x, password=1. Никаких специальных прав не требуется.
- **Шаги:** прочитать responses 401/422 в `/openapi.json`; выполнить запрос без cookie или запрос с ошибкой валидации; сравнить тело с описанной схемой.
- **Воспроизводимость:** 14/14 соответствующих проверок итоговой коллекции: 10 ответов 401 (R066…R075) и 4 ответа 422 (R009/R029/R044/R060).
- **Симптом:** нарушение контракта API; генераторы клиентов и автоматические проверки схем получают неожиданный формат.
- **Причина по инспекции:** штатные HTTPException / RequestValidationError FastAPI не нормализованы общим обработчиком, а в маршрутах вручную указаны другие схемы ошибок.
- **Обход:** клиент временно разбирает обе формы `detail`/`description`; это не устраняет несоответствие контракта. Исправление — согласовать обработчики и OpenAPI, затем повторить schema-проверки.
- **Доказательства:** [Postman HTML-отчёт](docs/lab4/evidence/newman.html), [OpenAPI](postman/openapi.json), [JSON](docs/lab4/evidence/newman.json). Stack trace, серверные пути и SQL в этих ответах не обнаружены.

## APP-07 — Перенос своей карточки в чужую приватную колоду разрешён

- **Статус:** Open. **Важность:** S2 Critical. **Срочность:** P1, исправить до публикации API.
- **Требование:** [NFR-02, UR-03](docs/requirements.md), ЛР4 пункт 3 — IDOR и защита чужих приватных данных от изменения.
- **Краткое описание:** проверяются права на исходную карточку, но не право изменения целевой колоды, чей ID передан в JSON.
- **Ожидаемый результат:** пользователь B отправляет `PATCH /v1/card/{своя карточка}/deck` с `deck_id` приватной колоды A; ответ 403; карточка остаётся в колоде B; список A не меняется.
- **Фактический результат:** 204; в приватной колоде A появляется вторая карточка пользователя B. Проверка списка A показывает 2 вместо ожидаемой 1.
- **Исходные данные:** два обычных пользователя A/B; отдельные приватные колоды; у каждого своя карточка; B знает UUID колоды A (секретность UUID не заменяет проверку прав).
- **Шаги:** создать материал A и B; войти как B; заменить `deck_id` в PATCH на UUID колоды A; войти как A и запросить список карточек его колоды.
- **Воспроизводимость:** 1/1 в итоговом прогоне, R090 и проверка сохранённого результата R095. Подмена была выполнена только на тестовых сущностях.
- **Симптом:** IDOR по идентификатору в теле запроса, нарушение целостности чужих данных.
- **Причина по инспекции:** `ChangeDeckCommandHandler` проверяет владельца текущей колоды и сразу вызывает `card.change_deck(...)`, не проверяя права на целевую колоду.
- **Обход:** надёжного пользовательского обхода нет; временное отключение операции переноса на доверенной границе уменьшает риск. Не полагаться на скрытые ID или UI.
- **Доказательства:** [Postman HTML-отчёт](docs/lab4/evidence/newman.html), R090/R095; [JSON](docs/lab4/evidence/newman.json). Прочие проверенные прямые IDOR-чтения и изменения отклонены; этот результат не позволяет объявить всю защиту доступа пройденной.
